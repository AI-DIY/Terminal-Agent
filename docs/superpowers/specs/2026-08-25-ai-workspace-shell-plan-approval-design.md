# Terminal-Agent AI 工作区图文对话与 Shell 计划审批设计

> 文档状态：待用户书面评审
> 设计基线：Terminal-Agent `1.0.11`，提交 `86d1785`
> 文档日期：2026-08-25
> 原型参考：`.superpowers/brainstorm/ui-20260811185554/content/simplified-core-workbench-v18-unified-ssh-connection.html`

## 1. 文档目的

本文档固化右侧“AI工作区”的产品、UI 和技术设计，使其在保持现有三栏工作台结构的前提下，支持：

- 文字聊天和仅限图片的图文聊天；
- AI 生成可渲染、可审批、可执行的整组 Shell 命令计划；
- 对 AI 原始命令进行安全围栏正则匹配；
- 围栏命中后的暂停、风险展示、人工修改和删除命令；
- 用户整组确认后，顺序向中间“Shell工作区”的在线 Shell 发送命令；
- 将首次执行结果作为独立审计消息追加到聊天末尾。

本次以快速开发为原则，不建设通用附件系统、复杂任务恢复、退出码跟踪、终端输出采集、再次执行或全自动驾驶。

## 2. 与既有设计的关系

本文档只修订右侧 AI 工作区及其与 Shell、安全围栏、模型和聊天存储的交互。现有左侧任务历史区、中间 Shell 工作区、SSH 连接、Shell 历史、本地主机记忆和设置页继续沿用当前实现。

当既有文档与本文档冲突时，以下规则以本文档为准：

1. 取消全自动驾驶，不再提供相关 UI、确认弹窗或自动发送分支。
2. 取消单条候选命令审批，改为整组计划一次审批。
3. 取消再次执行，不保留再次执行按钮或二次确认流程。
4. 安全围栏只匹配 AI 原始命令；人工修改后的命令不重新匹配。
5. 执行审计作为 `user` 角色的特殊消息追加到聊天末尾。

## 3. 范围

### 3.1 本次实现范围

- 微调右侧 AI 工作区布局和交互。
- 支持文字及图片输入，图片以内联 Data URL 保存。
- 根据当前聊天的完整历史决定使用 LLM 或 VLM。
- 使用 Node.js/TypeScript 版 `@langchain/langgraph` 编排结构化输出生成与修正。
- 定义并校验统一的 AI JSON 输出协议。
- 将聊天回复和执行计划分别渲染。
- 对计划中每条 AI 原始命令进行一次安全围栏匹配。
- 支持待审批计划的命令修改和单条删除。
- 支持整组一次确认并按步骤顺序发送到 Shell。
- 支持全部发送、部分发送和发送失败状态。
- 在聊天末尾持久化首次执行审计消息。
- 保持当前 AI 工作区默认宽度，并允许向左扩大到应用宽度的 45%。

### 3.2 明确不在范围内

- 全自动驾驶及任何无人工确认的命令执行。
- 已执行计划的再次执行。
- 单条命令独立审批。
- 人工修改后重新运行安全围栏。
- 命令退出码、标准输出、标准错误或业务执行结果解析。
- 等待 Shell 命令实际运行完成。
- 自动回滚、失败恢复、跨进程续跑或断点续传。
- 通用附件、附件表、附件目录、文件管理或非图片上传。
- 对聊天、命令、主机名、IP、业务路径、业务输出进行脱敏。
- 新建独立审计中心或审计日志页面。

## 4. 已确认的核心规则

1. AI 工作区始终采用人工确认执行模式。
2. AI 可以输出普通聊天回复，也可以同时输出一组有顺序的命令计划。
3. 计划整体审批一次，用户不会逐条审批。
4. 点击“确认并执行”即开始首次执行，不再弹出简短二次确认。
5. 首次执行无论全部发送还是部分失败，都必须追加一条审计消息。
6. 安全围栏命中后计划保持暂停，右侧展示命中规则、目标 Shell、AI 原始命令和风险说明。
7. 用户可以在确认前修改命令；修改后的命令不重新经过安全围栏。
8. 用户可以在确认前删除某一步；计划至少保留一个可执行步骤，删除最后一步应改为取消计划。
9. AI 原始命令和人工最终命令必须同时保留，供界面展示和审计使用。
10. 计划确认后立即锁定，不再允许修改或删除。
11. “已执行”只表示最终命令已成功写入目标 Shell，不表示命令返回成功。
12. 同一主机名存在多个在线 Shell 时，选择最早连接且仍在线的 Shell。
13. 计划确认后已绑定的 Shell 断开时，不切换到另一个同名 Shell。
14. 任一步写入失败或 Shell 断开时，停止当前及后续步骤，计划标记为部分执行或执行失败。

## 5. UI 设计

### 5.1 右侧区域尺寸

- 默认宽度保持 `390px`。
- 最小宽度保持 `340px`。
- 用户可拖动右侧分隔线向左扩大 AI 工作区。
- 最大宽度为当前应用客户区宽度的 45%，而不是固定 `520px`。
- 键盘调整分隔线时采用相同的动态上下限。
- 中间 Shell 工作区继续保留最低可用宽度；窗口变化时重新约束已保存宽度。

### 5.2 页面溢出

- 应用根节点、工作台和三栏主体使用客户区宽高与 `minmax(0, 1fr)` 约束。
- 页面根节点不得因固定最小高度或网格最小内容宽度产生浏览器级右侧、底部滚动条。
- AI 消息区、Shell 画布等确实需要滚动的内容，在各自内部滚动。
- 窄窗口下按钮、标签和长命令不得撑大页面宽度。

### 5.3 AI 标题区

标题区保留：

- `AI工作区`标题和辅助说明；
- 收起按钮；
- `人工确认执行`状态，明确“AI 计划不会自动运行”；
- 上下文用量。

移除：

- 辅助驾驶与全自动驾驶单选控件；
- 全自动驾驶升级入口；
- 全自动驾驶确认弹窗。

“立即压缩”放在上下文摘要同一行的独立操作位中。摘要文字、百分比和按钮使用可收缩网格或换行约束，不能互相遮挡。

### 5.4 AI 消息区

- 普通用户消息、普通 AI 回复、执行计划和执行审计使用不同视觉样式。
- AI 的聊天解释按普通消息渲染，不与命令代码混排。
- 计划说明使用普通说明文字样式，明确不发送到 Shell。
- 命令使用等宽字体和独立代码区域。
- 消息区只允许纵向滚动，长命令内部换行，不产生页面级横向滚动。
- AI 工作区未悬浮时隐藏消息区滚动条滑块；鼠标悬浮 AI 工作区时显示主题匹配的细滚动条。
- 隐藏滑块时保留稳定滚动槽占位，避免内容横向跳动。

### 5.5 图片输入

- 输入区提供图片选择按钮，使用现有图标库中的图片图标并提供悬停说明。
- 文件选择器只接受图片 MIME 类型。
- 选中图片后在输入区上方显示紧凑预览、文件名和移除按钮。
- 本次不显示或管理通用附件元数据，不支持文档、压缩包、音视频等文件。
- 发送后，图片与同一条用户文字共同形成一条多模态用户消息。
- 没有文字时允许仅发送图片。

### 5.6 窄宽度输入区

- 输入区底部使用可收缩布局。
- 图片按钮、关联 Shell 摘要、取消按钮和发送按钮不允许溢出容器。
- 宽度不足时，次要文字可以隐藏或截断；命令按钮保持可点击尺寸和完整图标。
- 不通过缩小到不可读字号解决溢出。

## 6. 执行计划卡片

### 6.1 卡片结构

一条合法 AI JSON 回复中如果 `plan` 不为 `null`，在普通聊天回复之后渲染执行计划卡片。卡片包含：

- 计划标题和计划标识；
- 当前状态；
- 步骤数量和目标 Shell 数量；
- 围栏命中汇总；
- 有序步骤列表；
- 整组操作区。

计划标识由主进程在持久化合法 assistant 消息时生成并保存，不能采用模型自行提供的标识。该标识在计划卡、计划内部状态和执行审计中保持一致。

每个步骤展示：

- 步骤序号；
- 目标主机名；
- 可获得时展示对应连接信息；
- 独立说明；
- `AI 原始命令`；
- 围栏命中标记；
- 修改按钮；
- 删除按钮。

说明文字从不进入 `SessionService.write()`。

### 6.2 围栏命中展示

任一步命中围栏时，卡片顶部展示：

- 命中规则名称；
- 目标 Shell；
- AI 原始命令；
- 风险说明；
- 命中的步骤编号。

计划保持待人工复核状态。围栏命中不产生自动发送，也不拆分成单条审批。

风险说明由本地应用根据围栏规则名称、正则表达式和固定模板生成，例如“AI 原始命令匹配高危删除规则，可能造成文件不可恢复删除”。它不是模型自由生成的计划说明，也不会发送到 Shell。现有规则不需要新增风险描述配置字段。

### 6.3 修改命令

- 修改只在待审批状态可用。
- 进入编辑态时，以 AI 原始命令作为初始内容。
- 保存后同时展示不可变的 AI 原始命令和标记为“人工修改”的最终命令。
- 最终命令必须是非空字符串，不能包含 NUL 字符。
- 保存人工修改后不重新运行安全围栏。
- 修改动作本身不执行命令。

### 6.4 删除命令

- 删除只在待审批状态可用。
- 删除后重新编号剩余步骤，并更新步骤数、目标 Shell 数和确认按钮文案。
- 被删除步骤不参与目标绑定、执行或执行审计中的最终命令列表。
- 计划至少保留一个步骤；只剩一个步骤时禁用删除并提示用户使用“取消计划”。

### 6.5 整组确认

- 所有计划都需要一次整组人工确认，不论是否命中安全围栏。
- 主要按钮文案为“确认并执行 N 步”。
- 点击后直接锁定计划并开始顺序发送，不再弹出第二个确认对话框。
- 确认后所有修改和删除入口永久禁用。
- 不显示“再次执行”按钮。

### 6.6 状态

计划至少包含以下应用状态：

| 状态 | 含义 | 可编辑 | 可执行 |
| --- | --- | --- | --- |
| `pending_review` | 等待用户确认，可能包含围栏命中 | 是 | 是 |
| `executing` | 已确认，正在按顺序发送 | 否 | 否 |
| `executed` | 所有保留步骤均成功写入目标 Shell | 否 | 否 |
| `partially_executed` | 至少一步已发送，随后失败并停止 | 否 | 否 |
| `execution_failed` | 第一步发送前或第一步写入时失败 | 否 | 否 |
| `cancelled` | 用户取消计划，未执行 | 否 | 否 |

界面可以显示中文状态，但不得把 `executed` 描述为命令业务执行成功。

## 7. AI 输出协议

### 7.1 最终 JSON

模型最终输出必须是一个完整 JSON 对象，JSON 外不得出现 Markdown、代码围栏或附加文字：

```json
{
  "version": 1,
  "reply": "中文聊天回复",
  "plan": {
    "title": "计划标题",
    "steps": [
      {
        "target": "web-02",
        "explanation": "独立展示且不执行的说明",
        "command": "可直接发送到 Shell 的命令"
      }
    ]
  }
}
```

纯聊天时：

```json
{
  "version": 1,
  "reply": "中文聊天回复",
  "plan": null
}
```

### 7.2 字段规则

- `version` 固定为 `1`。
- `reply` 是独立聊天回复，由消息气泡渲染，不执行。
- `plan` 为 `null` 或一个计划对象。
- `plan.title` 是简短计划标题。
- `plan.steps` 至少包含一个步骤。
- `target` 直接使用在线 Shell 的主机名，不生成临时别名。
- `target` 必须与当前任务关联的在线 Shell 主机名精确匹配。
- `explanation` 只用于用户理解，不发送到 Shell。
- `command` 必须是非空、可直接写入 Shell 的纯命令字符串，不能是 Markdown 代码块、自然语言占位符或包含 NUL 字符。

### 7.3 存储与渲染

- 合法的最终 JSON 以字符串形式原样保存到 `assistant.content`。
- 渲染器解析并分别展示 `reply` 与 `plan`。
- 模型生成的原始 JSON 不因人工修改而被覆盖。
- 人工编辑、删除、围栏命中、目标会话绑定和发送状态作为该 assistant 消息的可选应用内部计划状态保存。
- 应用内部计划状态不发送给模型，不引入独立通用计划表。

## 8. LangGraph.js 编排

### 8.1 选型

使用 Node.js/TypeScript 版：

```text
@langchain/langgraph
```

不引入 Python、Python 虚拟环境或单独的 Python 服务。

### 8.2 图职责

LangGraph.js 只负责编排以下最小流程：

```text
生成 JSON -> 校验 -> 修正 JSON -> 完成或失败
```

它不负责任务自动驾驶、Shell 调度、执行结果判断或长期任务恢复。

### 8.3 节点和状态

图状态至少包含：

- 当前模型消息；
- 当前原始输出；
- JSON 解析或语义校验错误；
- 已执行的修正次数；
- 最终合法结果。

节点职责：

1. `generate`：基于系统提示、聊天历史和当前 Shell 上下文生成 JSON。
2. `validate`：执行 JSON 解析、Zod 结构校验和目标/命令语义校验。
3. `repair`：将原始输出和明确的校验错误返回同一模型，请求只输出修正后的完整 JSON。
4. `complete`：返回最终合法 JSON。
5. `fail`：达到重试上限后返回统一错误，不暴露中间输出。

### 8.4 重试上限

- 首次生成最多调用模型一次。
- 校验失败后最多修正两次。
- 单次用户请求总模型调用次数最多三次。
- 每次修正后都重新执行完整结构和语义校验。
- 中间无效输出不展示、不持久化、不执行。
- 三次调用后仍无合法结果，聊天中保存一条普通可重试 AI 错误消息，不创建计划。

### 8.5 结构化输出兼容

- 对支持 OpenAI `response_format.json_schema` 的模型请求结构化输出。
- 不假设提供方一定遵守结构化输出；所有结果仍必须经过本地校验。
- Ollama、llama.cpp 或其他兼容实现忽略 `response_format` 时，修正循环继续生效。
- 复用现有 `ModelProviderRouter` 和 Chat Completions 客户端，不新建第二套模型配置系统。

## 9. 图文消息与模型路由

### 9.1 消息格式

聊天消息保持接近 OpenAI Chat Completions：

```json
{
  "role": "user",
  "content": [
    { "type": "text", "text": "请检查这张截图" },
    { "type": "image_url", "image_url": { "url": "data:image/png;base64,..." } }
  ]
}
```

- 现有纯文本历史继续允许 `content` 为字符串。
- 新图文消息使用 `text` 与 `image_url` 内容块。
- 首版直接保存 Data URL，不新增附件目录或附件服务。
- `assistant.content` 继续是最终 JSON 字符串。

### 9.2 路由规则

主进程读取持久化后的当前聊天完整历史，判断是否出现过 `image_url` 内容块：

| 模型设置 | 当前聊天历史是否出现图片 | 路由结果 |
| --- | --- | --- |
| LLM + VLM | 否 | LLM |
| LLM + VLM | 是 | VLM |
| 仅 VLM | 任意 | VLM |

一旦当前聊天任一历史消息出现图片，该聊天后续请求持续使用 VLM。新建的无图片聊天仍使用 LLM。

渲染进程不得传入可被信任的 `hasImages` 结论；最终路由必须由主进程根据持久化聊天计算。

## 10. 安全围栏

### 10.1 匹配时机

- 只在 AI 最终 JSON 首次通过校验后，对每个步骤的 `command` 匹配一次。
- 使用现有 `RegexRuleSettingsService.match()`。
- 匹配对象是不可变的 AI 原始命令。
- 每个步骤保存命中的规则标识和规则名称，用于后续渲染和审计关联。

### 10.2 人工修改

- 人工修改后的最终命令不重新匹配安全围栏。
- 原因是安全围栏用于拦截 AI 输出，不用于拦截用户主动修改的指令。
- 不论命令是否修改、是否命中过围栏，都必须由用户整组确认后才能发送。

### 10.3 内容安全边界

以下业务内容不进行脱敏：

- 聊天文字和图片；
- AI 回复、计划说明和命令；
- 主机名、IP、业务路径；
- 经用户授权的结构化主机事实；
- 执行审计中的最终命令。

以下认证材料继续隔离，不能进入模型请求或聊天持久化：

- API Key；
- SSH 密码；
- 私钥内容；
- 私钥口令；
- AccessClient 临时桥接密码；
- 令牌和环境变量值。

## 11. Shell 目标解析与执行

### 11.1 主机名解析

- AI 协议只包含真实主机名，不生成临时别名。
- 用户确认计划时，主进程从当前在线 `SessionService.snapshot()` 中解析每个目标。
- 同一主机名有多个在线 Shell 时，选择 `SessionService` 有序会话集合中的第一个，即最早连接且仍在线的会话。
- 为计划中的目标锁定具体 `sessionId` 后，不因后续同名 Shell 变化而重新路由。

### 11.2 顺序发送

用户点击整组确认后：

1. 锁定当前计划，禁止后续编辑和删除。
2. 按当前保留步骤解析并锁定目标 `sessionId`。
3. 严格按步骤顺序调用 `SessionService.write(sessionId, command + "\n")`。
4. 每次成功写入后，将对应步骤标记为已发送。
5. 某一步的 Shell 已断开或写入抛错时，标记该步骤失败。
6. 停止发送当前失败步骤之后的所有步骤，并标记为未发送。
7. 根据结果将计划标记为 `executed`、`partially_executed` 或 `execution_failed`。
8. 追加执行审计消息。

不读取终端输出，不等待提示符，不判断退出码，也不推断命令的业务结果。

## 12. 聊天存储与执行审计

### 12.1 消息主体

消息记录继续以 Chat Completions 核心字段为主体：

- `role`；
- `content`。

现有消息标识、聊天标识、时间和流式状态继续作为应用字段保留。为本功能只增加必要的可选字段，不建设新的通用消息格式。

### 12.2 审计消息

执行完成或中断后，在聊天末尾追加：

```json
{
  "role": "user",
  "messageType": "execution_audit",
  "content": "【执行审计】计划 EP-001 部分执行……"
}
```

规则：

- `role` 固定为 `user`。
- `messageType` 是应用内部字段，用于独立渲染样式。
- 第一次执行必须生成审计消息。
- 因为不支持再次执行，所以每个计划最多生成一条执行审计。
- 审计内容包括计划标识、执行状态、目标主机、已发送步骤、失败或未发送步骤以及实际最终命令。
- 审计不包含原始终端输出、退出码、界面点击细节或中间模型修正输出。

### 12.3 发送给模型

- 精简审计内容需要进入后续模型上下文，帮助 AI 识别哪些命令已经发送，避免重复规划。
- 构建 Chat Completions 请求时，只映射提供方允许的字段。
- `messageType`、计划 UI 状态、围栏详情和发送状态等应用内部字段必须被删除。
- 审计的 `role` 和 `content` 保留，因此模型看到的是一条普通 `user` 历史事实。
- 系统提示必须明确：`【执行审计】` 是应用记录的历史事实，不是用户发出的新执行指令，不能据此重复执行。

## 14. 错误处理

### 14.1 模型输出失败

- JSON 解析、结构校验、目标校验或命令校验失败时进入修正节点。
- 两次修正仍失败，持久化普通可重试 AI 错误消息。
- 不展示原始无效 JSON，不创建半成品计划，不运行围栏，不执行命令。

### 14.2 模型或网络错误

- 沿用现有超时、取消和连接错误归一化。
- 修正调用也受同一个用户请求取消信号和总超时边界控制。
- 用户取消时不继续后台修正，也不持久化计划。

### 14.3 目标 Shell 不可用

- 生成阶段发现 `target` 不属于当前任务的在线主机名时，作为语义校验错误请求模型修正。
- 用户确认时目标已离线，则该目标步骤发送失败。
- 已锁定目标离线后不自动切换同名 Shell。
- 失败后停止剩余步骤并追加审计。

### 14.4 写入失败

- `SessionService.write()` 抛错即视为该步骤未成功发送。
- 已经成功写入的步骤保持已发送状态。
- 后续步骤保持未发送状态。
- 不重试写入，避免重复命令。

### 14.5 持久化失败

- 计划确认前若无法持久化锁定状态，则不得开始发送命令。
- 命令发送后若审计持久化失败，界面必须显示明确错误，不能伪装为审计已保存。
- 本次不增加后台补偿队列；应用保留当前计划发送状态，用户可重新加载核对。

## 15. 最小测试范围

### 15.1 单元测试

1. AI JSON：合法纯聊天、合法计划、非法 JSON、代码围栏、空命令、未知目标和最多两次修正。
2. 模型路由：无图片聊天走 LLM；当前或历史出现图片后走 VLM；仅 VLM 模式始终走 VLM。
3. 消息映射：多模态内容块正确持久化；`messageType` 和计划内部状态不会进入提供方请求。
4. 安全围栏：只匹配 AI 原始命令一次；人工修改不重新匹配；删除步骤后不执行该步骤。
5. Shell 解析：同名在线 Shell 选择最早连接者；锁定后断开不切换。
6. 顺序发送：全部成功、首步失败、中途失败、后续停止以及首次审计内容。

### 15.2 渲染器测试

- 普通回复与计划分开渲染。
- 围栏命中信息完整展示。
- 待审批可修改、可删除，确认后锁定。
- 不存在全自动驾驶和再次执行入口。
- 图片选择、预览、移除和发送状态正确。
- `340px` 最小宽度下底部按钮和文字不溢出。
- “立即压缩”不被遮挡。
- 滚动条仅在悬浮 AI 工作区时显示滑块。

### 15.3 集成与端到端测试

保留一条核心端到端流程：

1. AI 返回包含多步命令的合法 JSON。
2. 其中一步命中安全围栏。
3. 用户修改命中命令并删除另一条命令。
4. 用户整组确认一次。
5. 最终命令按顺序写入目标 Shell。
6. 计划锁定并显示已执行或部分执行。
7. 聊天末尾出现 `execution_audit` 消息。

同时在桌面窗口常用尺寸和最小支持尺寸检查无页面级右侧、底部滚动条。

## 16. 验收标准

1. 用户能发送纯文字、纯图片或图文消息。
2. 当前聊天历史出现图片后，后续请求由主进程持续选择 VLM。
3. 前端永远不会看到或保存 LangGraph.js 中间无效输出。
4. AI 回复和命令计划具有明显不同的渲染格式。
5. 说明文字不会发送到 Shell。
6. 围栏命中时完整展示规则、目标 Shell、原始命令和风险说明。
7. 人工修改不重新运行围栏，但仍必须整组确认。
8. 用户可以删除某一步，且被删除命令不会执行。
9. 用户只确认一次整组计划，随后命令按步骤顺序写入 Shell。
10. 同名 Shell 始终选择最早连接且仍在线的会话，锁定后不自动替换。
11. 中途断开或写入失败会停止剩余步骤并显示部分执行或失败。
12. 已确认计划永久禁止编辑和删除。
13. 首次执行后聊天末尾出现一条独立样式的执行审计。
14. 模型请求中不包含 `messageType` 等应用内部字段，但包含精简审计正文。
15. 页面没有全自动驾驶或再次执行功能。
16. AI 工作区默认 `390px`、最小 `340px`，最大可拖到应用宽度的 45%。
17. 上下文压缩按钮、悬浮滚动条和窄宽度底部按钮均符合已确认原型。
18. 应用页面最右侧和最下侧不出现非业务滚动条。

## 17. 实施原则

- 以当前 `1.0.11` 代码为基线，不恢复已经移除的业务内容脱敏逻辑。
- 优先扩展现有聊天、模型路由、围栏和 SessionService 边界，不另建重复服务。
- 新增抽象只服务于 JSON 编排、计划状态和模型消息映射。
- 先保证结构化输出、人工审批和顺序发送闭环，再处理视觉细节。
- 不借本次功能重构无关的任务标题、置顶、诊断工具、AccessClient 或 Shell 历史功能。
